# Unity C# 코드 리뷰 기준

## 1. 리뷰 원칙

- 변경된 코드에서 실제로 발생할 가능성이 있는 문제를 우선한다.
- 변경 사항의 의도, 호출 관계, 관련 상태 및 주변 코드를 함께 확인한다.
- 문제를 발견하면 파일 위치, 원인, 발생 조건, 예상 결과를 구체적으로 설명한다.
- 가능하면 현실적인 수정 방법이나 간단한 코드 예시를 제시한다.
- 변경 사항과 직접 관련 없는 기존 문제는 참고사항으로 구분한다.
- 확실하지 않은 내용은 사실처럼 단정하지 않는다.
- 프로젝트 규모와 개발 단계를 고려해 개선안을 제안한다.
- 디자인 패턴, 인터페이스, 추상화, 최적화를 무조건 강제하지 않는다.
- 문제가 발견되지 않았다면 불필요한 지적을 생성하지 않는다.

## 2. 중요도 기준

### Critical

즉시 수정해야 하는 치명적인 문제.

- 정상적인 사용 중 발생하는 치명적인 크래시
- 저장 데이터 손상이나 복구 불가능한 상태
- 심각한 보안 취약점
- 핵심 기능 전체의 사용 불가능

### High

기능 오류나 심각한 성능 저하로 이어질 가능성이 높은 문제.

- 주요 게임 기능의 오작동
- 잘못된 상태 전환으로 인한 진행 불가
- 반복적으로 발생하는 런타임 예외
- 명확한 메모리 누수 및 심각한 성능 문제
- 기존 Scene, Prefab, 데이터와의 호환성 문제

### Medium

안정성, 유지보수성, 확장성을 위해 수정이 권장되는 문제.

- 특정 조건에서 발생하는 상태 불일치
- 불필요한 반복 연산 및 메모리 할당
- 코드 중복과 과도한 클래스 간 결합
- 변경 비용을 높이는 설계 구조
- 예외 상황에 대한 처리 부족

### Low

선택적으로 개선할 수 있는 사항.

- 가독성 및 네이밍 개선
- 의미가 불명확한 매직 넘버
- 간단한 코드 중복 및 단순화
- 경미한 구조 개선

중요도는 문제 발생 가능성, 영향 범위, 재현 조건을 고려해 결정한다.

단순한 스타일 차이에는 불필요하게 높은 중요도를 부여하지 않는다.

## 3. 가독성과 유지보수성

### 네이밍

- 클래스, 메서드, 변수 이름이 역할과 의도를 명확하게 나타내는가?
- `data`, `value`, `temp`, `manager`처럼 지나치게 포괄적인 이름을 남용하지 않는가?
- bool 변수는 상태나 조건을 자연스럽게 읽을 수 있는가?
- 메서드 이름은 수행하는 동작을 명확하게 표현하는가?
- 프로젝트 내에서 일관된 네이밍 규칙을 사용하는가?

좋은 bool 변수 이름 예시:

```csharp
isDead
canAttack
hasTarget
```

### 매직 넘버

의미를 파악하기 어려운 숫자나 문자열이 코드에 직접 사용되고 있는지 확인한다.

```csharp
if (currentLevel >= 10)
{
    damage *= 1.5f;
}
```

게임 규칙에서 특별한 의미를 가진 값이라면 상수 또는 설정값으로 분리하도록 제안한다.

```csharp
private const int SpecialLevel = 10;
private const float DamageMultiplier = 1.5f;
```

Inspector에서 조정해야 하는 값이라면 `[SerializeField]` 사용을 고려한다.

주요 검토 대상:

- 체력, 공격력, 이동속도
- 쿨타임 및 지속시간
- 확률과 데미지 배율
- 경험치 및 레벨 기준
- 레이어 번호
- 애니메이션 상태 값
- 씬 인덱스
- 최대 개수와 제한 횟수

단, `0`, `1`, `-1` 등 관용적으로 사용되는 값이나 의미가 명확한 값까지 무조건 상수로 분리하지 않는다.

### 코드 중복과 복잡도

- 동일한 상태 판단이나 로직이 여러 곳에서 반복되는가?
- 메서드가 지나치게 많은 역할을 수행하는가?
- 중첩 조건문 때문에 제어 흐름을 파악하기 어려운가?
- 불필요한 임시 변수와 중간 단계가 존재하는가?
- 작은 수정으로 해결할 문제에 과도한 구조 변경을 제안하고 있지 않은가?

## 4. 객체지향 설계

### 묻지 말고 시켜라 (Tell, Don't Ask)

객체의 내부 데이터를 외부에서 가져와 상태를 판단하고 행동을 결정하는 구조를 확인한다.

```csharp
if (player.Health <= 0)
{
    player.Die();
}
```

가능하다면 객체가 자신의 상태와 행동을 관리하도록 한다.

```csharp
player.TakeDamage(damage);
```

`Player`는 `TakeDamage()` 내부에서 체력 감소, 사망 판단, 사망 처리, 이벤트 발생 등을 수행할 수 있다.

검토 항목:

- 객체의 내부 상태를 외부에서 반복적으로 판단하는가?
- 여러 클래스에 동일한 상태 판단이 중복되는가?
- Getter와 프로퍼티를 통해 내부 구현이 과도하게 노출되는가?
- 상태 변경과 관련된 책임이 적절한 객체에 있는가?

단, UI 표시, 디버깅, 저장 및 직렬화처럼 단순 조회가 자연스러운 경우에는 행동 메서드로 변경하도록 강제하지 않는다.

### 응집도와 결합도

- 하나의 클래스에 서로 관련 없는 책임이 섞여 있는가?
- 관련된 데이터와 동작이 적절하게 묶여 있는가?
- 클래스가 너무 많은 다른 클래스를 직접 참조하는가?
- 구체적인 구현에 지나치게 의존하는가?
- 작은 변경이 여러 클래스의 수정으로 이어지는가?
- Singleton과 전역 상태에 불필요하게 의존하는가?
- 클래스 간 순환 참조가 발생하는가?

구조적인 문제가 명확하다면 어떤 책임을 분리하고 객체 간 의존성을 어떻게 개선할지 구체적으로 제안한다.

## 5. SOLID 원칙

SOLID는 설계를 평가하기 위한 기준으로 사용한다.

모든 클래스에 인터페이스나 디자인 패턴을 적용하도록 강제하지 않는다.

### SRP: 단일 책임 원칙

- 클래스가 하나의 명확한 책임을 담당하는가?
- 서로 다른 이유로 변경되는 기능이 하나의 클래스에 과도하게 모여 있는가?
- 관련 기능을 분리했을 때 결합도와 변경 비용이 실제로 감소하는가?

예를 들어 `Player`가 입력, 이동, 공격, 체력, 사운드, UI까지 모두 처리한다면 책임 분리를 검토한다.

```text
PlayerInput
PlayerMovement
PlayerCombat
PlayerHealth
PlayerAnimation
```

단, 메서드가 많다는 이유만으로 컴포넌트를 분리하지 않는다.

### OCP: 개방-폐쇄 원칙

- 새로운 기능이나 타입을 추가할 때 기존 조건문을 계속 수정해야 하는가?
- 반복적으로 증가하는 타입 분기가 유지보수를 어렵게 만드는가?
- 상속, 전략 패턴, 컴포지션 등을 이용한 확장이 실제로 유리한가?

변경 가능성이 낮고 간단한 조건문에는 불필요한 추상화를 강제하지 않는다.

### LSP: 리스코프 치환 원칙

- 자식 클래스가 부모 클래스의 동작 계약을 지키는가?
- 자식 클래스가 부모 기능을 사용할 수 없어 예외를 던지는가?
- 자식 타입 때문에 사용하는 쪽에서 별도 타입 검사를 추가해야 하는가?

상속 관계가 부자연스럽다면 컴포지션이나 인터페이스를 고려한다.

### ISP: 인터페이스 분리 원칙

- 클래스가 사용하지 않는 기능까지 구현하도록 강제되는가?
- 하나의 인터페이스에 서로 관련 없는 기능이 섞여 있는가?
- 역할별 인터페이스 분리로 의존성을 줄일 수 있는가?

```text
IMovable
IAttackable
IFlyable
ISwimmable
```

단, 의미 없는 소규모 인터페이스의 무분별한 생성을 권장하지 않는다.

### DIP: 의존성 역전 원칙

- 상위 수준의 게임 로직이 특정 구현 클래스에 강하게 의존하는가?
- 구현 교체나 테스트가 어려운 구조인가?
- 인터페이스, 의존성 전달, 이벤트 등을 이용해 결합도를 줄일 필요가 있는가?

Unity에서는 상황에 따라 다음 방식을 고려한다.

- Inspector 기반 컴포넌트 참조
- 메서드 및 생성자를 통한 의존성 전달
- 인터페이스를 구현한 컴포넌트
- ScriptableObject 기반 데이터 분리
- 이벤트 기반 상호작용

## 8. Unity 직렬화 및 에셋 참조

- `[SerializeField]` 필드의 이름이나 타입 변경으로 기존 직렬화 데이터가 손실될 가능성이 있는가?
- 필드 이름 변경 시 `[FormerlySerializedAs]` 적용이 필요한가?
- Scene 및 Prefab의 Inspector 참조가 깨질 가능성이 있는가?
- ScriptableObject 원본 설정과 런타임 상태를 적절하게 분리하는가?
- 에셋 이동, 삭제, 교체 과정에서 `.meta` 파일과 GUID 참조가 유지되는가?
- Animator Parameter 이름이나 타입 변경이 기존 Animator와 호환되는가?
- Animation Event가 참조하는 메서드에 변경이 있는가?
- Prefab, Scene, Animation 등 코드 외부의 연결 관계에 영향을 주는가?

직렬화 필드나 에셋 참조가 변경되었다면 관련 Scene, Prefab 및 설정의 영향 범위를 확인한다.

직접 확인할 수 없는 에셋 참조 문제는 확정적인 오류로 보고하지 않고 추가 검증 항목으로 구분한다.

## 9. Unity 성능

### 반복 실행 코드

- `Update()`, `FixedUpdate()`, `LateUpdate()`에서 불필요한 객체 할당이 발생하는가?
- 호출 빈도가 높은 코드에서 불필요한 탐색이나 연산이 반복되는가?
- 문자열 생성, LINQ, 박싱 등으로 GC 할당이 반복되는가?
- 동일한 값을 매 프레임 불필요하게 계산하는가?
- 불필요한 컬렉션 생성이나 복사가 발생하는가?

### 오브젝트 탐색

- 씬 전체 탐색이 반복 실행되는가?
- 동일한 컴포넌트 참조를 불필요하게 반복 검색하는가?
- 캐싱이 실제로 성능과 가독성을 개선하는가?

`GetComponent()`를 사용했다는 이유만으로 성능 문제라고 단정하지 않는다.

### 오브젝트 생성

- `Instantiate()`와 `Destroy()`가 지나치게 자주 반복되는가?
- 객체 생성 및 제거 비용이 실제 병목이 될 가능성이 있는가?
- Object Pooling 도입이 복잡도 증가보다 더 큰 이점을 제공하는가?

### 성능 판단 원칙

- 호출 빈도, 객체 수, 할당량, 실행 환경을 고려한다.
- 성능 측정 없이 최적화 효과를 수치로 단정하지 않는다.
- 실제 비용이 작고 코드가 단순한 경우 불필요한 최적화를 강제하지 않는다.
- 최적화로 복잡도가 증가한다면 예상 이점과 유지보수 비용을 함께 고려한다.

- Rigidbody 관련 물리 처리가 적절한 실행 시점에 이루어지는가?
- 물리 기반 이동에 고정 시간 간격을 적절하게 사용하는가?
- 프레임 기반 이동과 시간 기반 이동을 혼동하는가?
- `Time.deltaTime`과 `Time.fixedDeltaTime`을 의도에 맞게 사용하는가?
- 충돌 이벤트가 여러 번 발생해 데미지 등이 중복 적용될 가능성이 있는가?
- 충돌 레이어와 트리거 조건이 코드의 의도에 맞는가?
- `Time.timeScale` 변경으로 인해 의도하지 않은 동작이 발생하는가?
- 일시정지 및 재개 이후 타이머나 물리 상태가 정상적으로 유지되는가?

---

## 11. Coroutine 및 비동기 생명주기

- Coroutine의 시작과 종료 시점이 적절한가?
- 같은 Coroutine이 중복 실행될 가능성이 있는가?
- 오브젝트가 비활성화되거나 파괴된 이후에도 관련 작업이 남을 가능성이 있는가?
- 비동기 작업이 완료되었을 때 참조 대상이 유효한가?
- 필요한 경우 작업 취소 및 중복 실행 방지가 구현되어 있는가?
- `WaitForSeconds`와 `WaitForSecondsRealtime`을 게임 시간 정책에 맞게 사용하는가?
- `Time.timeScale`이 0인 상황에서도 정상 동작해야 하는 로직인가?

Coroutine, Invoke, async 작업은 각각 실제 종료 및 취소 동작이 다르므로 사용한 API의 동작을 기준으로 검토한다.

---

## 12. 게임 플레이 상태 관리

- 사망, 피격, 공격, 스킬 사용이 의도치 않게 중복 처리되는가?
- 무적, 경직, 쿨타임 등의 상태 전환이 일관되게 관리되는가?
- 이벤트나 콜백의 실행 순서로 인해 상태 불일치가 발생하는가?
- 게임 상태에 따라 입력, 이동, 공격이 적절하게 제한되는가?
- 동일한 데미지가 중복 적용될 가능성이 있는가?
- 사망한 객체가 계속 행동하거나 보상을 여러 번 지급하는가?
- 씬 전환 및 게임 재시작 이후 상태가 적절하게 초기화되는가?
- 일시정지와 재개 과정에서 의도하지 않은 상태가 유지되는가?

모든 상태를 하나의 관리 클래스로 통합하도록 강제하지 않는다.

실제 상태 불일치, 중복 실행, 기능 오류가 발생할 가능성이 있을 때 개선을 제안한다.

---

## 13. Object Pooling

오브젝트 풀링을 사용하는 코드에서는 다음 항목을 확인한다.

- 재사용 시 체력, 속도, 타이머, 상태 플래그가 초기화되는가?
- 이전 사용에서 실행된 Coroutine이나 비동기 작업이 남아 있는가?
- 이벤트 구독이 중복되거나 이전 참조가 유지되는가?
- Rigidbody의 속도와 물리 상태가 초기화되는가?
- ParticleSystem, TrailRenderer, Animator 등의 시각적 상태가 초기화되는가?
- 이전 타겟이나 충돌 정보가 남아 있는가?
- 재활성화 시 초기화 순서에 문제가 발생하는가?
- 풀로 반환된 객체가 다른 시스템에서 여전히 사용되는가?

풀링을 사용하지 않는 코드에 대해서는 반복 생성 비용이 실제 문제가 될 가능성이 높은 경우에만 도입을 제안한다.

## 14. 설계 구조 개선 제안 기준

다음 문제가 명확할 때 구조 개선을 제안한다.

- 하나의 클래스가 지나치게 많은 책임을 담당한다.
- 동일한 조건문이나 상태 판단이 여러 클래스에 반복된다.
- 새로운 기능을 추가할 때 기존 코드의 광범위한 수정이 필요하다.
- 객체들이 서로의 내부 구현에 강하게 의존한다.
- 상속 관계가 부모 클래스의 계약을 위반한다.
- Singleton이나 전역 상태 의존성으로 테스트 및 확장이 어렵다.
- 클래스 간 순환 의존성이 존재한다.

구조 개선을 제안할 때는 다음 내용을 설명한다.

1. 현재 구조에서 실제로 발생하는 문제
2. 분리하거나 변경해야 할 책임
3. 변경 후 클래스 또는 컴포넌트의 역할
4. 객체 간 상호작용 방법
5. 기대 효과 및 추가 복잡도

단순히 SOLID 원칙에 더 부합한다는 이유만으로 구조 변경을 요구하지 않는다.

현재 변경과 관련된 명확한 개선 가치가 있을 때 우선 제안한다.

## 15. 변경 영향 및 검증

- 변경된 메서드를 호출하는 다른 코드에 영향이 있는가?
- public API, 이벤트, 인터페이스 변경으로 기존 기능이 깨지는가?
- 정상 상황뿐 아니라 경계값과 예외 상황에서도 동작하는가?
- 기존 테스트에 영향을 주는가?
- 추가 테스트가 필요하다면 어떤 상황을 확인해야 하는가?
- 코드 외부의 Scene, Prefab, Inspector 설정에 영향이 있는가?
- 수정된 코드에 대해 실제 확인한 범위가 무엇인가?

코드만으로 검증할 수 없는 사항은 별도로 명시한다.

실행하거나 확인하지 않은 테스트를 통과했다고 표현하지 않는다.

## 16. AI 리뷰 오탐 방지

AI는 다음 규칙을 반드시 준수한다.

- 확인된 문제와 잠재적 위험을 구분한다.
- 버그라고 판단했다면 발생 조건과 원인을 설명한다.
- 관련 코드를 충분히 확인하지 않고 문제를 단정하지 않는다.
- 프로젝트의 Unity 버전과 패키지 환경을 고려한다.
- 다른 클래스에서 이미 처리하는 기능을 중복으로 요구하지 않는다.
- 단순한 스타일 차이를 기능 오류처럼 보고하지 않는다.
- 미세한 성능 차이를 심각한 성능 문제처럼 표현하지 않는다.
- 불필요한 인터페이스, 추상화, 디자인 패턴을 강제하지 않는다.
- 동일한 원인에서 발생한 문제를 여러 항목으로 중복 보고하지 않는다.
- 코드 위치와 문제 발생 조건을 특정할 수 없다면 확정적인 지적으로 작성하지 않는다.
- 수정으로 얻는 이점보다 복잡도가 커지는 개선을 무조건 권장하지 않는다.
- 문제가 발견되지 않았다면 문제를 억지로 만들어내지 않는다.

리뷰의 목표는 가능한 한 많은 문제를 지적하는 것이 아니라, 실제로 수정할 가치가 있는 문제를 정확하게 발견하는 것이다.

## 17. 리뷰 결과 형식

다음 형식으로 답변한다.

### 총평

변경 목적과 전체적인 평가를 2~3문장으로 작성한다.

### 발견된 문제

각 문제는 중요도가 높은 순서대로 정리한다.

**[중요도] 문제 제목**

- **위치:** 파일 경로 및 코드 위치
- **문제:** 어떤 문제가 있는가?
- **발생 조건:** 어떤 상황에서 발생하는가?
- **영향:** 실제로 어떤 결과가 발생할 수 있는가?
- **수정 제안:** 어떻게 해결할 수 있는가?

가능하다면 간단한 코드 예시를 포함한다.

### 설계 개선 제안

실제 구조적인 문제가 명확한 경우에만 작성한다.

- 현재 구조의 문제
- 개선할 클래스 및 책임
- 객체 간 상호작용
- 기대 효과와 비용

### 추가 검증 필요 사항

코드만으로 확인할 수 없는 사항이나 실행이 필요한 테스트를 작성한다.

검증하지 않은 내용을 확인된 오류로 표현하지 않는다.

### 잘 작성된 점

실제로 잘 작성된 부분이 있을 때만 간단히 작성한다.

### 최종 요약

- Critical: 발견 건수
- High: 발견 건수
- Medium: 발견 건수
- Low: 발견 건수
- 추가 검증 필요: 발견 건수

문제가 발견되지 않았다면 확인한 범위와 함께 문제가 발견되지 않았음을 명시한다.

## 최종 원칙

**실제로 발생할 수 있는 버그와 위험한 변경을 최우선으로 검토한다.**

**설계 개선은 실질적인 이점이 명확할 때 제안한다.**

**근거 없는 문제를 만들어내거나 불필요한 리팩터링을 강제하지 않는다.**
